Querylane is a self-hosted, PostgreSQL-first workspace for understanding multiple servers. It keeps live operations, database structure, access, and permitted rows in 1 browser surface.

Use the overview to establish a baseline before investigating a database:

1. Confirm connection state, PostgreSQL version, and the sample timestamp.
2. Review active, idle, and idle-in-transaction connections.
3. Compare sampled transactions, cache, storage, and connection metrics across the incident window.
4. Expand health checks for connectivity, pressure, statistics access, and replication.
5. Open a database when the question moves from server health to structure or data.

Querylane keeps healthy sections available when 1 probe fails. A partial warning is not the same as a disconnected server.

## Investigate live activity

Activity is a live, read-only session view. Filter by database, role, application, state, or wait condition. Sort by query or transaction age, inspect full query and client context, and follow explicit blocking relationships.

<img
  alt="Blocking chain from a root blocker to waiting and downstream sessions"
  height="580"
  loading="lazy"
  src="/images/docs/diagrams/blocking-sessions.svg"
  width="1120"
/>

Read every arrow from left to right as “the session on the left blocks the session on the right.” Start with a node that has no incoming blocking arrow. A waiting session can block more work behind it, so the oldest query is not automatically the root blocker.

Refresh immediately before acting through another tool. Querylane does not currently cancel queries or terminate sessions.

For a slow database:

1. Establish the incident window on the instance metrics.
2. Check live sessions, old transactions, waits, and blocking chains.
3. Use Query insights to compare cumulative time, mean time, calls, rows, and buffer behavior.
4. Inspect table indexes, size, partitions, and sequential-scan evidence.
5. Write a testable diagnosis before changing PostgreSQL.

Query insights requires `pg_stat_statements` and sufficient statistics visibility. Missing data is reported as unavailable rather than displayed as zero.

Data Explorer moves from a database and schema map to the details of 1 table or view.

| Surface | What it answers |
| --- | --- |
| Data | Which permitted rows match filters and sorts? |
| Columns | What are the types, defaults, generated values, and comments? |
| Keys and constraints | What rules and relationships shape the data? |
| Indexes | Which methods, columns, predicates, and expressions exist? |
| Partitions | What are the parent, children, strategy, and bounds? |
| Policies | Which row-level security roles and predicates apply? |
| Triggers | Which functions run for each event and timing? |
| Definition | How is the PostgreSQL object defined? |

Large values can appear as bounded previews. Copy and export fetch complete values first. 1 action resolves up to 100 oversized cells. If a full-value read fails or the selection exceeds that limit, Querylane stops instead of producing a plausible but incomplete result. Download `bytea` values from the row detail drawer.

Exports contain selected rows from the currently loaded result, not every matching database row. CSV, JSON, and SQL formats are available. CSV neutralizes values spreadsheet software could interpret as formulas. Use PostgreSQL `COPY` or backup tooling for bulk, authoritative, or recoverable data movement.

Follow one access check from left to right, then down to PostgreSQL verification. Membership can supply privileges at several layers, but every required database, schema, and object check still matters. Row-level security can narrow the rows after the object privilege passes.

The graph explains catalog evidence; it is not a policy engine. PostgreSQL remains the authority. Confirm sensitive decisions with privilege functions or an approved session as the subject role.

### Review row-level security

Row-level security runs after ordinary object grants. Querylane shows policy roles, commands, permissive or restrictive mode, `USING`, and `WITH CHECK` expressions. Its visibility preview explains policy composition but does not execute a query as the selected role. Owners, superusers, and roles with `BYPASSRLS` can produce a different result from ordinary application roles.

<div class="docs-diagram-wide">

Follow the decision from left to right, then down to the row checks. PostgreSQL first checks ordinary access. Roles that bypass row-level security stop before policy evaluation. Everyone else needs at least 1 applicable permissive policy; restrictive policies can only narrow that result. `USING` controls existing rows, while `WITH CHECK` controls proposed rows for writes.

## What Querylane offers today

| Area | What you can do |
| --- | --- |
| Instances | Register multiple PostgreSQL servers and inspect identity, connection state, metrics, and health |
| Activity | Inspect sessions, transaction age, clients, waits, and blocking relationships |
| Data Explorer | Browse schemas and objects, map relationships, inspect metadata, filter rows, and export selected data |
| Roles and access | Explore roles, memberships, grants, definitions, and effective-access paths |
| Database insights | Review extensions, database health, query patterns, and table-level statistics |

The tools optimize for different jobs:

- Choose **pgAdmin** for mature PostgreSQL administration and broad write workflows.
- Choose **DBeaver or DataGrip** for desktop SQL work across database engines.
- Choose **Drizzle Studio** when work should stay centered on 1 Drizzle project's schema and data.
- Choose **Querylane** when the primary job is understanding a PostgreSQL fleet from 1 operational workspace.

## Current boundary

Querylane is deliberately read-first. It does not yet replace a mature SQL IDE, backup tool, or write-heavy administration surface. SQL Workbench, row editing, session actions, and broader administration writes remain planned, with safety rails before broad mutation support.

Anyone who can reach Querylane can use the visibility granted to its PostgreSQL roles. Protect the application with authenticated ingress before adding production credentials. See [Deploy Querylane](/get-started/deploy-querylane).
