Querylane needs exactly one thing from you to run: a PostgreSQL database of its own, the **metadata database**. Everything else is optional.

## The metadata database

Querylane stores its state in one PostgreSQL database that it owns:

- the PostgreSQL **instances** you registered and their encrypted credentials;
- metrics and health **samples** collected from every instance;
- catalog caches and background-job state.

It is not one of the servers you inspect. Keep it separate: a dedicated database with a dedicated login, backed up like any other application database.

```sql
CREATE ROLE querylane LOGIN PASSWORD 'replace-me';
CREATE DATABASE querylane OWNER querylane;
```

Querylane creates and migrates its own tables at startup, so the login must own the database. Any PostgreSQL works, including managed services such as RDS, Cloud SQL, or Neon.

## Configuration modes

| Mode | When to use it | How |
| --- | --- | --- |
| **First-launch wizard** | Trying Querylane, or a small installation you manage from the browser | Start without configuration; the wizard asks for the metadata database |
| **Environment variables** | Containers and Kubernetes; secrets come from your platform | Set `QUERYLANE_DATABASE_DSN` and `QUERYLANE_INSTANCE_SECRET_KEY` |
| **YAML file** | Configuration as code; instances should be versioned, not clicked | `querylane server start --config querylane.yaml` |
| **Embedded PostgreSQL** | A single process on one machine with no PostgreSQL at hand | Choose it in the wizard or set `embedded:` in YAML |

The modes combine. The common production shape is a YAML file for non-secret settings plus environment variables for the DSN and key; the [Helm chart](/get-started/install-helm) and [Compose examples](/get-started/install-docker) are built that way.

### First-launch wizard

Start Querylane with no metadata database configured and open it in the browser. The wizard lets you connect an external PostgreSQL, use embedded PostgreSQL, or shows the YAML to write. Once the database is ready you register your first instance in the UI.

The wizard writes to `~/.querylane/config.yaml` (or the `--config` path) when that location is writable. In a container it usually is not, so prefer environment variables there.

### Environment variables

```sh
QUERYLANE_DATABASE_DSN="postgres://querylane:***@db.example.com:5432/querylane?sslmode=require"
QUERYLANE_INSTANCE_SECRET_KEY="$(openssl rand -base64 32)"   # generate once, keep forever
```

`QUERYLANE_HTTP_HOST` and `QUERYLANE_HTTP_PORT` override the listener (default `0.0.0.0:8080`). Environment variables take precedence over the YAML file.

### YAML file

```yaml querylane.yaml
http:
  host: "0.0.0.0"
  port: 8080

# Metadata database. Prefer QUERYLANE_DATABASE_DSN in the environment
# so the password stays out of the file.
database:
  dsn: "postgres://querylane:***@db.example.com:5432/querylane?sslmode=require"

# Optional: register instances here instead of in the UI.
instances:
  - id: production
    display_name: "Production"
    host: "db.example.com"
    port: 5432
    database: "app"
    username: "querylane_reader"
    password_env: "PRODUCTION_DATABASE_PASSWORD"
    ssl_mode: require
    labels:
      env: production
```

When `instances` is present, the file owns instance configuration and the UI's instance editor becomes read-only. `password_env` and `dsn_env` read secrets from the environment at connect time, so nothing sensitive is written to the file or the metadata database. Remove the section to manage instances in the UI again.

Querylane watches the file and applies instance changes without a restart. The complete, commented reference with every key is [`docs/reference-config.yaml`](https://github.com/querylane/querylane/blob/main/docs/reference-config.yaml).

### Embedded PostgreSQL

For a direct run on one machine, Querylane can start its own PostgreSQL. The wizard always creates persistent storage in `~/.querylane/pgdata` when the home directory is writable and chooses the first free port starting at `5433`. In YAML:

```yaml querylane.yaml
embedded:
  mode: persistent        # or ephemeral: state is gone at shutdown
  data_path: "~/.querylane/pgdata"
  port: 0                 # 0 = first free port from 5433
```

Do not use embedded PostgreSQL in a container without a persistent volume, or with more than one replica.

## The instance secret key

`QUERYLANE_INSTANCE_SECRET_KEY` encrypts instance passwords entered in the UI before they are written to the metadata database. Without it, Querylane refuses to save UI-entered passwords; instances defined in YAML with `password_env` do not need it.

Generate it once and treat it like a database password:

```sh
openssl rand -base64 32
```

:::warning
Every replica and every restart must receive the exact same value. Changing or losing the key makes stored instance credentials unreadable, and rotation is not supported yet.
:::

## Run more than one replica

Querylane is stateless apart from the metadata database, so you can run several replicas behind one load balancer. All replicas must share:

- the same metadata database — replicas coordinate through it, including which replica collects metrics for a given instance, so each instance is sampled once rather than once per replica;
- the same `QUERYLANE_INSTANCE_SECRET_KEY`;
- the same configuration and the same network access to your instances.

Live-query limits in `limits:` are per replica; multiply by the replica count when sizing connection budgets on busy servers.

## Verify

```sh
curl --fail --request POST \
  --header 'Content-Type: application/json' \
  --data '{}' \
  http://localhost:8080/querylane.console.v1alpha1.ConsoleService/GetConsoleConfig
```

`"state":"STATE_READY"` means the metadata database is connected and migrated. A `failed_precondition` error means Querylane is serving but the metadata database is not configured yet. See [Operate Querylane](/get-started/operate-querylane#troubleshoot) if setup fails.
