---
title: Deploy Querylane
description: Run Querylane durably: an external metadata database, one stable secret key, a reverse proxy that authenticates users, and a read-only role on each server.
---

The [quick start](/get-started/install-docker) is for evaluation. A deployment that survives restarts and that other people use needs four things beyond it: a PostgreSQL database Querylane can keep its metadata in, one secret key that never changes, a reverse proxy that authenticates users, and a dedicated role on every server you register.

:::warning
Querylane does not currently include built-in authentication. Do not expose it directly to the public internet. Put it behind a trusted private network or a reverse proxy that enforces authentication and TLS.
:::

## Production shape

- **Reverse proxy** terminates TLS and authenticates users, then forwards to Querylane on port `8080`.
- **Querylane** is a single container. It needs two environment variables: `QUERYLANE_DATABASE_DSN` and `QUERYLANE_INSTANCE_SECRET_KEY`.
- **Metadata PostgreSQL** stores Querylane's own state (registered instances, encrypted credentials, collected metrics). Any PostgreSQL server you back up will do.
- **Your PostgreSQL servers** are reached with a dedicated, limited role per server.

Querylane reads its secrets only from environment variables. It does not integrate with an external secret manager; keep the two values wherever you already keep secrets (a Kubernetes Secret, a `.env` file with mode `0600`, your cloud's secret store) and inject them into the container's environment.

## 1. Create the metadata database

On a PostgreSQL server you back up:

```sql
CREATE ROLE querylane LOGIN PASSWORD 'replace-me';
CREATE DATABASE querylane OWNER querylane;
```

Querylane runs its schema migrations at startup, so back this database up before every upgrade. Do not use the embedded PostgreSQL for anything beyond a single-node demo.

## 2. Generate the secret key

```sh
openssl rand -base64 32
```

`QUERYLANE_INSTANCE_SECRET_KEY` encrypts the instance passwords entered in the UI before they are stored. Generate it once and store it next to the metadata DSN in your secret store; every restart and every replica must use the exact same value. Changing or losing it makes existing encrypted instance credentials unreadable, and key rotation is not currently supported.

## 3. Run the container

Pin a release tag from `ghcr.io/querylane/querylane` (`latest` is fine for evaluation, not for something you upgrade deliberately). A minimal `compose.yaml`:

```yaml
services:
  querylane:
    image: ghcr.io/querylane/querylane:0.1.0
    environment:
      QUERYLANE_DATABASE_DSN: "${QUERYLANE_DATABASE_DSN}"
      QUERYLANE_INSTANCE_SECRET_KEY: "${QUERYLANE_INSTANCE_SECRET_KEY}"
    ports:
      - "127.0.0.1:8080:8080"
    restart: unless-stopped
```

Put the two values in a `.env` file next to it:

```sh
chmod 600 .env
docker compose up --detach
docker compose logs --follow querylane
```

The loopback binding assumes the reverse proxy runs on the same host. If the proxy is another container, remove `ports`, put both on a private Docker network, and proxy to `querylane:8080`.

On Kubernetes, use the [Helm chart](/get-started/install-helm) instead; it takes the same two values.

Settings beyond the two environment variables (CORS origins, allowed target networks, connection limits) are optional and live in a YAML file. See [Configure Querylane](/get-started/configure-querylane) when you need them.

## 4. Put a proxy in front

Expose only the Querylane HTTP service on port `8080`, never PostgreSQL or the container runtime. The proxy has to authenticate users: SSO through an identity-aware proxy, a VPN, or at minimum a password.

With Caddy, a password-protected deployment is a hash and a few lines:

```sh
caddy hash-password
```

```nginx
querylane.example.com {
  encode zstd gzip

  basic_auth {
    operator $2a$14$replace_with_caddy_hash
  }

  reverse_proxy 127.0.0.1:8080
}
```

Use Caddy `forward_auth` (or the equivalent in your proxy) with your identity provider when you need SSO, groups, or centralized revocation. Cloudflare Tunnel works too, but the tunnel alone does not authenticate anyone; attach an Access policy before sharing the hostname.

Check that a signed-out browser gets a challenge and that the host's public IP does not answer on port `8080`.

## 5. Create a role on each server you register

Give Querylane its own login on every PostgreSQL server instead of reusing an application or superuser account. A read-only role with `pg_monitor` unlocks everything Querylane shows today: schema browsing, data reads and exports, activity, health, statistics, and query insights.

```sql
CREATE ROLE querylane_reader
  LOGIN
  PASSWORD 'replace-me'
  INHERIT
  NOSUPERUSER
  NOCREATEDB
  NOCREATEROLE
  NOREPLICATION
  NOBYPASSRLS;

GRANT CONNECT ON DATABASE app TO querylane_reader;
GRANT pg_monitor TO querylane_reader;
```

Then, connected to each database you want browsable:

```sql
GRANT USAGE ON SCHEMA app_schema TO querylane_reader;
GRANT SELECT ON ALL TABLES IN SCHEMA app_schema TO querylane_reader;

ALTER DEFAULT PRIVILEGES FOR ROLE app_owner IN SCHEMA app_schema
  GRANT SELECT ON TABLES TO querylane_reader;
```

Skip the `SELECT` grants if operators should only see the catalog and server health, or drop `pg_monitor` if they should only browse schemas. Do not grant `SUPERUSER`, `BYPASSRLS`, or ownership solely for Querylane; row-level security keeps applying to this role.

## More than one replica

Querylane is stateless apart from the metadata database, so several replicas can sit behind one load balancer. They must share the same metadata database, the same `QUERYLANE_INSTANCE_SECRET_KEY`, the same configuration and target policy, and the same network access to your servers. Do not use embedded PostgreSQL for a multi-replica deployment. Live-query limits are process-local, so the total load Querylane can put on a server grows with the replica count.

`GET /` answers as soon as the process is up; for a readiness check, call `ConsoleService.GetConsoleConfig` as shown under [Verify](/get-started/configure-querylane#verify).

Continue with [Operate Querylane](/get-started/operate-querylane) for backups, upgrades, and troubleshooting.
